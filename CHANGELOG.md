# Changelog

## Unreleased

- native UI draws transforms, shadows and complete gradients, and JXML has attributes for them (`docs/jxforge.md`): `translateX`, `translateY`, `scaleX`, `scaleY` and `rotate` (degrees, clockwise, about the centre of the node's bounds, as JavaFX) are drawn for the node and its subtree by Skia and NanoVG, and picked through the inverse transform (a moved, scaled or rotated button is clicked where it shows, its handler gets the position in its own space, layout bounds do not change, such a node is never skipped for being outside the window); the software renderer moves and scales uniformly and draws a rotation or an uneven scale unrotated/unscaled (picking still follows the transform); `elevation` (with `shadowColor`, `shadowOffsetX`, `shadowOffsetY`) draws a blurred shadow under a box (Skia mask blur, NanoVG box gradient, a smoothstep approximation in the software renderer); `gradient` takes a CSS `linear-gradient`/`radial-gradient` with every stop, and the CSS subset of `jxparallel-fx` now passes all stops of `-fx-background-color` gradients (not only the first), translate/scale/rotate values and `DropShadow` effects to the renderer; new `JXPainter` primitives `transform`, `shadow`, `fillGradient`; screens that use none of it paint byte-identically (goldens unchanged); the NanoVG path was checked in a hidden OpenGL window of the test machine only, the `jxparallel-fx` changes were not compiled (JDK 8 only module); animating these values over a duration is not provided yet

- JXForge: FXML to JXML (`FxmlToJxml`, `docs/jxforge-fxml.md`): an existing `.fxml` screen is converted to the JXML tree the interpreter and the compiler read (layout panes, the common controls, placement, `onAction` handlers, `${controller.x}` bindings, `%key` through a `ResourceBundle`, `fx:include`, `fx:define` toggle groups, table/list/tree models, inline styles), by the Maven goal `jxforge:fxml` (then `generate`), the command line `com.jxparallel.forge.FxmlToJxml`, or `JxmlTemplate.readFxml(...)` with no text in between; whatever it cannot map is an entry (file, line, element, attribute, reason) in an `FxmlReport`, `--strict` / `strict` fails on it, and every `fx:id` is listed because node injection has no equivalent in the native UI.
- native UI and JXForge: the calendar of a `DatePicker`, the cells of a `TimePicker` and the swatches of a `ColorPicker` highlight what is under the pointer and take the keys while open: arrows (a day or a week in the calendar, Page Up / Page Down a month, the nearest neighbouring cell in the grids), Home and End, Enter or Space to choose; typing in the color picker's hex field is unchanged; the calendar, time and color popups draw the highlight
- native UI and JXForge: `accelerator="Ctrl+S"` on a `MenuItem` or `Button` now binds the key: the item's or button's `onAction` runs from anywhere in the window, even with its menu closed, unless an open menu or popup, a selecting list or a focused text field takes the key first (held keys do not repeat it; disabled, hidden, disabled-menu and closed-dialog items do not run); `JXKeyEvent` gets `isRepeat()`; the accelerator text was already drawn at the right of a menu row
- native UI: menus by keyboard: F10, or Alt pressed and released alone, opens the first enabled menu of the `MenuBar` with its first row highlighted (F10 again closes it), and the Menu key or Shift+F10 opens the `ContextMenu` of the focused node; the arrows, Enter, letters, submenus and Escape are the existing popup navigation; the titles have no mnemonics, so there is no Alt+letter (`JXNativeNode.toggleMenuBar()`, `JXAltTap`; the Alt tap on Windows is not yet checked in a real window)
- native UI and JXForge: files dropped on a window from the file manager go to the nearest element under the pointer with an `onDrop` handler (`JXNativeNode.dispatchDrop`, logical coordinates; JXML `onDrop="#dropFiles"` calls `dropFiles(List<String> paths)`, a new `STRINGS` handler value in the interpreter and the compiler); `JXWindow` feeds it from `glfwSetDropCallback` (not yet run in a real window)
- native UI: `JXWindow` sets its icon (`setIcon(w, h, argb)`, `setIcons(List<JXWindowIcon>)`, `setIconFile(s)`, `setIconFiles(s...)` through `JXImages`, several sizes) and gets the window calls a desktop application needs: `setMaximized`, `setIconified` / `minimize`, `restore`, `setFullScreen`, `requestFocus`, `setAlwaysOnTop`, and `setResizable`, `setDecorated`, `setFloating` that now work on an open window, with their getters and `getX` / `getY`; all posted to the display thread (the GLFW calls are compiled, not yet run in a real window)
- native UI: the mouse cursor follows what is under the pointer: `JXCursor.at` / `JXNativeNode.cursorAt` (free of GLFW, tested) give the I-beam over text fields, password fields and text areas, the hand over hyperlinks, the horizontal or vertical resize cursor over a `SplitPane` divider that has an `onChange`, the arrow elsewhere, and the `cursor` of the deepest element that has one; JXML `cursor="hand|text|default|crosshair|h-resize|v-resize"` on any tag. `JXWindow` shows it with GLFW standard cursors created once and destroyed on close (not yet run in a real window)
- native UI fonts (`jxparallel-ui`, `com.jxparallel.ui.text`): `JXFonts` registers fonts from a file, a stream or a classpath resource under a family name and finds installed fonts by family name (the system font folders of Windows, Linux and macOS are scanned once, reading each file's `name`, `OS/2` and `head` tables in plain Java, `.ttc` collections included); a `JXFont` (family, numeric weight, italic) resolves to the nearest real face of the family, bold and italic are never synthesized; `fontFamily`, `fontWeight` and `italic` on the props of `Label`, `Button`, `TextField`, `PasswordField`, `TextArea`, `CheckBox`, `ToggleButton`, `RadioButton` and `Hyperlink` (JXML attributes of the same names, `bold` keeps working, nothing is inherited from a parent, as `fontSize` is not); measuring, Skia, NanoVG and the software painter use the same face; a character the font lacks (CJK, Arabic, Hebrew, emoji, symbols) comes from a fallback face that has it, found among the registered fonts, well-known system families and then every installed family, and Skia draws colour emoji from the system's colour emoji font (seen with Segoe UI Emoji; NanoVG and the software renderer are monochrome or empty for bitmap emoji fonts); text mixing left-to-right and right-to-left runs is itemized by bidi level, script and font and shown in the right visual order (`JXShapedText`: the runs HarfBuzz shaped, which the three renderers draw and `JXTextEngine.width` adds up); before this, `hb_buffer_guess_segment_properties` gave the whole string the direction and script of its first letters; caret movement and selection inside right-to-left text still follow the logical order, and NanoVG, which does not shape, draws a right-to-left run in reverse character order (Hebrew is right, joined Arabic letters are not); UI font and bold text without these props are drawn and measured as before (goldens unchanged); not yet seen in a real window, NanoVG not run on 32-bit

- native UI is HiDPI-aware: `JXWindow` reads the monitor content scale (and follows it when the window changes monitor), keeps layout, hit-testing, `setSize` and pointer coordinates in logical pixels, and draws at the physical resolution with Skia, NanoVG and the software painter; `-Djx.scale=1.5` forces the scale and `JXWindow.getScale()` returns it; pixel snapping stays logical, scale 1 output is unchanged (not yet checked on a real 125/150/200% display)
- native `Image` loads picture files: `JXImages` (`jxparallel-ui`, `load(Path)`, `load(InputStream)`, `load(byte[])`, `loadResource(Class, String)`, `load(String source)`, `find`, `preload`) decodes PNG, JPEG and the first frame of GIF and BMP with stb_image (`lwjgl-stb`, added to the base dependencies and the three native profiles) into the ARGB `int[]` the renderers already take, so Skia, NanoVG and the software painter need no change, and the decoded pictures are kept in a bounded cache (64 pictures, 64 MB) so a file is decoded once; JXML `<Image src="logo.png"/>` (also `src="${photoPath}"`) is resolved against the folder of the `.jxml` file, the same in the interpreter and in the generated classes, and the node takes the picture's own size unless `fitWidth`, `fitHeight` or `preserveRatio` say otherwise; a missing or corrupt file draws nothing and is reported once on `System.err`; SVG is not read
- JXForge and native UI: hover and keyboard in the popups and menus: the option or menu row under the pointer is highlighted (the chosen option turns grey meanwhile); in an open `ComboBox` list Up, Down, Home, End, Page Up and Page Down move the highlight, Enter or Space choose it and a letter jumps to the next option that starts with it; in a `MenuButton`, `ContextMenu` or `MenuBar` the same keys move over the rows that can be chosen (wrapping round), Enter or Space run the item, Right opens a submenu (or the next menu of a bar) and Left closes it; Escape closes and gives the focus back to the control; a closed `ComboBox`, picker or `MenuButton` that has the focus opens with Alt+Down, F4 or Space; `routeKey` returns the node that has the focus afterwards, and the characters of keys an open menu took are not typed into the focused field (`docs/jxforge.md`, "Overlays"); not yet in the calendar and the time and color grids

- JXForge and native UI: lists, tables and trees select their rows themselves, the application still holding the state: `selected="@{current}"` (the row, -1 for none, `onSelect`) and, with `selectionMode="multiple"`, `selection="@{picked}"` (a `double[]`, `onSelection`) on `ListView`, `TableView`, `Tree` and `TreeTable`; a click selects, Ctrl+click toggles and Shift+click extends a range, Up, Down, Home, End, Page Up and Page Down move the selection and scroll it into view (Shift extends, Ctrl+A selects all), a double click or Enter runs the row's `onAction`, the list takes the focus with Tab, and the selected rows are drawn with the look's selection colour (grey when the list is not focused); a selected row outside the built window is kept, and a list without these attributes is as before (`docs/jxforge.md`, "Selection of rows")

- JXForge and native UI, work that JXML still lost to JavaFX (`docs/jxforge-optimizations-2026-10-21.md`): `<For memo="true">` keeps the elements of a large loop while the controller, the list and the window are the same (checked: the body reads only its own loop variables), and the tree rows are made only for the window (a `Tree` update went from 20 MB to 0.1 MB allocated); `JXPaint` skips nodes outside the window (pixel-identical, tested on all 94 components) and the software painter blends translucent spans with less work; the reconcile and the native nodes make less garbage; measured again on 84 components, Java 17: build 19x, ready to paint 86x, 47x less memory retained, 7.9x less CPU; tiny updates and text input paint are still behind JavaFX

- JXForge (`jxparallel-forge`, `jxforge-maven-plugin`): native screens written in JXML, widget-style tags (`Column`, `Row`, `Grid`, `Tabs`, `TextField`...), compiled at build time into plain Java classes that build the `JXElement` tree with direct calls, or read at runtime by an interpreter with the same rules; `${a.b}` bindings (`${a.b()}` for records), `#method` handlers checked by `javac`, `<Slot>` for components written in Java, constant subtrees built once; one schema table gives every prop the type the native renderer reads (see `docs/jxforge.md`); on 20 form screens, compiled builds 30 to 40x faster than interpreting the file when warm and in half the time cold on Java 17 and 21 (little gain cold on the Java 8 32-bit client VM), about 10 to 26% faster than a cached template once the native nodes are laid out (`docs/jxforge-benchmark-2026-10-21.md`); the 1.0 widget scope (91 components of the JavaFX, Flutter and Compose catalogs, see `docs/jxforge-1.0.md`) is implemented with overlays, trees, styles, includes and a live-reload view, and every component is measured one by one against JavaFX (`docs/jxforge-components-benchmark-2026-10-21.md`)

## 0.1.0 (2026-10-26)

- first release on Maven Central, group `io.github.bacuriim` (the Java packages stay `com.jxparallel`): `jxparallel-core`, `-ui`, `-junit4`, `-junit5`, `-mockito`, `-powermock`, `-fx`, `-fx-controlsfx` (built on JDK 8), `-javafx`, `-fxml` (built on OpenJFX 21); the poms carry the license, developer and SCM data Central asks for, and the `release` profile adds sources, Javadoc, GPG signatures and the upload (see RELEASING.md)

- fixed: Skija crashed the JVM while loading its native library on Java 8 64-bit; the cause is the `io.github.humbleui:types` 0.1.1 it brings, compiled for Java 9 (the library looks up `Rect`, `IRect`, `Point`... on load and uses the failed lookup); `jxparallel-ui` now depends on `types` 0.2.0 (the same API plus two `contains` methods, compiled for Java 8), and the whole ui suite, Skia images included, runs on Java 8 64-bit; Java 8 still paints with NanoVG unless `-Djx.renderer=skia`

- fixed: a reconcile that changed a tooltip's text, a combo or choice box's prompt, or a text area's row count kept the node's old size, so the text was cut and its neighbours stayed where they were (the native layer of `ComboBox.setPromptText` and `TextArea.setPrefRowCount` after the screen was shown); `sizeAffected` now names every prop the size code reads, and `JXSizePropsReconcileTest` changes each one in place and compares with a fresh mount

- builds on JDK 8 use Mockito 4.11 (profile `mockito-java8`, activated by the JDK), since Mockito 5 needs Java 11; JDK 11 and later keep Mockito 5
- native mode on 32-bit: a frame of about 44 ms a few seconds after start-up is gone; the client VM compiles a native method's wrapper on the calling thread when it gets hot (about 15 ms each), so the NanoVG natives are now warmed on a background thread one second after the first frame (`JXNanoVGRenderer.startWarmCalls`, client VM only); measured with a synchronized 239 Hz display, the native worst frame is 5.2 ms against JavaFX's 15.9 ms, and no time, CPU or memory metric is significantly worse than JavaFX on 32 or 64-bit (`docs/fx-backends-comparison-2026-09-29.md`)

- native mode of `jxparallel-fx` (`-Djx.backend=native`, phase 2b): every JX node is a `NativeModel` drawn by `jxparallel-ui`; the common JavaFX controls (labels, buttons, toggles, radio and check boxes, hyperlinks, text fields and areas, password fields, combo and choice boxes, spinners, date pickers with calendar, sliders, progress bars and indicators, scroll panes, virtualized list and table views, tab panes, titled panes, accordions, pagination, button bars, text flows, images, tooltips, context menus), Modena look shared by Skia and NanoVG (`JXPaint`), JavaFX event semantics (filters, handlers, consume, accelerators, focus traversal, default and cancel buttons, drag and drop), a CSS subset with specificity, dialogs and alerts in a nested event loop with the Windows button order, file choosers (tinyfd), ControlsFX notifications, window modality, snapshots, and labels sized with the running JavaFX's own line metrics
- native mode starts the display thread, the OpenGL driver, fonts and painting classes in the background at startup (`JXDisplay.prewarm()`), in parallel with the application building its screen: on a large-form screen on Java 8 32-bit the first frame comes about 35% sooner than with plain JavaFX; list and table cells scrolled out of view are reused for the rows scrolling in, like JavaFX's `VirtualFlow`
- native mode renders incrementally: a frame rebuilds only the elements of changed nodes and their ancestors (subtrees for CSS-relevant and inherited changes, hover, pressed and focus), and reuses the rest as the same instances, which the reconcile skips; table cells listen to their value like `TableCell`; on a large-form screen, allocation while updating every frame dropped from 360 to 38 MB and the application thread's CPU from 609 to 125 ms (plain JavaFX: 266 ms)
- native reconcile by key: elements carry a `key`, and `JXNativeNode` matches children with distinct keys by key rather than by position, so a row that stays on screen while scrolling keeps its node and element and is only moved (one-row scrolling allocates 14% less); fixed (native mode): a cell's reference to its table (`tableView`, `tableRow`, `listView`, `toggleGroup`, `owner`...) invalidated the whole table and its cell pool as if the table had moved
- native scrolling allocates about a third of plain JavaFX's (52 against 148 MB on a large-form table, 32-bit): `JXProps` stores its props in one flat array, layout constraint keys are constants, a JX `PropertyValueFactory` is read directly (`valueFor`), setting up cells no longer makes the list or table being built stale, CSS results are cached per render for each set of matched rules, keyed reconcile allocates no maps, number properties are watched without boxing; `FxBackendBench` reports allocation per thread
- JX `Simple*Property` makes its JavaFX peer on first need (a listener, a binding, JavaFX reading it) and holds its value until then, so an application model costs one object per property as with JavaFX (100,000 rows: 42 MB native, 45 MB on JavaFX, against 57 MB before); subclasses get their peer at once; generated by `scripts/make-lazy-properties.py`
- native tab panes: a `Tab`'s selection or classes no longer rebuild its content (it is not the content's CSS parent, as in JavaFX), the native nodes of tabs that leave are kept (`retainChildren`), and the other tabs are built while the window is idle, so a first switch finds them ready; tab switching allocates 1.2 MB against JavaFX's 1.9
- native start-up: the window the prewarm makes to load the OpenGL driver becomes the first window instead of a second context being created (about 140 ms of CPU on 32-bit)
- `FxBackendBench`: `-Dbench.threads=true` prints the start-up CPU per thread; `first_frame_process_cpu_ns`
- fixed (native mode): selected table rows were not shown as selected
- fixed (native mode): adding a node to a second parent left it in the first one as well; it now moves, like JavaFX
- native mode performance, from measuring a large-form screen against plain JavaFX (`docs/fx-backends-comparison-2026-09-29.md`, `scripts/FxBackendBench.java`, `scripts/measure-fx-backends.ps1`): cached class simple names and dispatch keys (Java 8 does not cache `getSimpleName`), cached JavaFX defaults, table cells read their observable value instead of calling the value factory every frame, no OpenGL context switch per frame, JavaFX's software pipeline by default in native mode (it draws nothing there), fewer copies and boxes per frame; `NativeFrames` reports presented frames to measurement tools; on Java 8 32-bit the native backend now uses 12% less CPU than plain JavaFX on that screen (it used 38% more than the JX API on JavaFX before these changes)
- native transitions: `FadeTransition`, `TranslateTransition`, `ScaleTransition`, `RotateTransition`, `ParallelTransition` and `SequentialTransition` of native nodes run on a JavaFX animation (`NativeAnimations`); the generator routes inherited `Animation` methods through `Fx.peerAs`
- native `ScrollPaneSkin` and `TitledPaneSkin`: shown scroll and titled panes get a skin whose `viewRect` exists, as applications read it by reflection
- fixed (native mode, found by mutation-driven tests): consuming an event no longer skips the other handlers of the same node; getters of unset values report JavaFX's defaults (read from a prototype of the JavaFX class); `RadioButton.fire()` outside a group toggles; `selectPrevious()` from no selection selects the last item; `ComboBox.setValue` outside the items clears the index; `TabPane` starts on its first tab and its selection model drives the tabs; slider arrow keys follow the orientation; combo box cell factories receive a `ListView`; `MapValueFactory` cells show their value; `fireEvent` copies and window/dialog events carry the right source; dialog `onShowing`/`onShown`/`onHiding`/`onHidden` run; `ScrollPane` honours `hmin`/`hmax`/`vmin`/`vmax`; `GridPane.addRow`/`addColumn` account for spans; the spinner editor follows `increment()`/`decrement()`; `RadioMenuItem` joins its toggle group; `Scene.getAccelerators()` and `Node.getProperties()` return JavaFX's maps; headless tests use an in-memory clipboard
- fixed: tooltips had no size and showed only their text; labels with `wrapText` never wrapped (now sized for the width set on them, checked against JavaFX)
- testing: golden image and exact primitive recordings of every control state, boundary tests found by mutation testing (PIT: 95% of the new layout, text and painting mutants and 78% of the native runtime's killed), headless native-mode suites for controls, interaction, dialogs, CSS, drag and drop, runtime and animations
- native `separator`, `titled` (TitledPane) and `accordion` elements, with the JavaFX 21 / Modena sizes: 3 px horizontal and 6 px vertical separators, a 25 px title bar with arrow, a 1 px content border, a collapsed pane reduced to its title, Modena's 0.8em padding on layout-pane content, and the accordion giving the expanded pane the height the others leave; checked against real JavaFX on 500 random trees (`JXTitledDifferentialTest`); `jxparallel-fx` native mode maps `Separator`, `TitledPane` and `Accordion` (only `expandedPane` is open, like JavaFX); clicking a title does not toggle it yet
- `jxparallel-fx`: JavaFX-compatible API under `com.jxparallel.fx` (same class names as JavaFX): 424 classes generated from JavaFX 8 by `scripts/GenerateFxApi.java` plus the application launcher, `ObservableList` and `FXMLLoader` by hand; each JX object currently runs on a JavaFX peer, and everything crossing the boundary (nodes, lists, enums, events, listeners, lambdas) is converted by `com.jxparallel.fx.Fx`; JavaFX calls methods a JX subclass overrides (`updateItem`, `call`, `toString`...); the `FXMLLoader` parses each file once (neutral `FxmlTemplate`) and builds JX objects from unchanged FXML, including Scene Builder output, `fx:include`, `@` locations and `fx:constant`; `jxparallel-fx-controlsfx` covers ControlsFX `Notifications` and `CustomTextField`; `scripts/migrate-imports.py` rewrites imports and qualified names without touching any other byte
- layout containers: `border` (BorderPane), `grid` (GridPane with column/row constraints and spans), `pane`, `anchor` (AnchorPane), `flow` (FlowPane) and `tile` (TilePane), plus padding and child margins everywhere; each checked against real JavaFX 21 on 1000 random trees; sizes may be negative like in JavaFX
- layout: min/pref/max sizes, grow priorities, alignment and fill flags with the JavaFX 21 VBox, HBox and StackPane algorithms and pixel snapping, checked against real JavaFX on 1000 random trees; controls use JavaFX sizes (buttons keep their width, text fields stretch); default font 12 px like JavaFX; a change that leaves a node's sizes unchanged no longer relayouts its parent
