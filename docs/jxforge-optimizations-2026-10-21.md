# JXForge: what was still behind JavaFX, and what changed

The [per-component benchmark](jxforge-components-benchmark-2026-10-21.md) showed where compiled JXML was
behind the JavaFX controls. This page records the causes that were found, what was changed, and the same
series measured again after the changes. Both series are kept: `docs/components-2026-10-21/` (before) and
`docs/components-2026-10-21-after/` (after), same machine, same method (84 components, 3 JVMs, 5 runs in a
fresh JVM each, 8 passes, fixed 512 MB heap), same inputs except that the `Tree` and `TreeTable` screens
now use `<For memo="true">` (the screens are generated by `scripts/generate-component-bench.py`).

## Causes and changes

The causes were found with a probe that splits one update into building the elements, reconciling them
and laying out (bytes and milliseconds of each), with JFR allocation and CPU samples, and by reading the
code.

| Behind | Cause | Change |
|---|---|---|
| `Tree` / `TreeTable` update: 20 to 24 MB and 3 to 7 ms | Not the reconcile (27 to 100 KB): the screen **built 10,000 items per tree on every update**, and `JxmlRuntime.tree` then listed all of them to take a window of 30 | `<For memo="true">` keeps what a loop built while the controller, the list and the window are the same; `JxmlRuntime.tree` counts the items in one pass and makes objects only for the rows of the window. The update allocates 0.1 MB. |
| Painting: 5,000 nodes painted for 30 in the window | `JXPaint` painted every node | A node above or below the clip is skipped (32 px margin); a container only when none of its descendants reaches the clip; overlay hosts and floating nodes never |
| Text fields: 91% of the paint time in one loop | A translucent rectangle redid the whole source-over for every pixel | The source half is made once per span; same arithmetic, tested on every pixel |
| Small updates: 64 to 168 B per node in the reconcile | A key set and two iterators in `sizeAffected`, a new override array in every `setProps` | Indexed access to the props (`JXProps.size/keyAt/valueAt`), the array is kept |
| Every native node | A list, a read-only view of it, a zero-length array and a consumer, even for a leaf | A leaf shares an empty list; the others are made when needed |
| Building an element | The props array always had room for 8, an empty varargs array per leaf | `JXProps.builder(n)` with the size the compiler knows; `JXElement.of(type, props)` |

`<For memo>` is opt-in, and checked: its body may read only its own loop variables, because a value of the
controller would go stale ([docs/jxforge.md](jxforge.md)). To change what a memo loop shows, give it another
list; an item edited in place is not seen.

## What was verified

- Tests: core 34, ui 257, forge 113 (7 new for `memo`, interpreter and compiler agreeing, with hoisting on
  and off), examples-native 35, fx 250; Java 8, 17 and 21 where the module runs there.
- Pixels: all 94 components, in both value sets, are painted with and without the skipping and the buffers
  compared whole: 188 frames, 0 differences. The paint checksum and the fingerprint of the 84 measured
  components are identical in both series. A mutation (ignoring the descendants of a container) is caught
  by a test.

## Result, Java 17 x64

Geometric mean over the 43 components that have a JavaFX counterpart; how many times better compiled JXML is
than the JavaFX control.

| | Before | After |
|---|---:|---:|
| Build, cold / warm | 19.7x / 16.7x | 20.1x / 19.1x |
| Ready to paint, cold / warm | 4.9x / 79.6x | 5.0x / 85.6x |
| Update one prop | 4.4x | 4.9x |
| Paint (indicative) | 3.4x | 7.4x |
| Memory allocated: build / ready / update | 15.2x / 78.2x / 1.8x | 19.9x / 107.2x / 2.7x |
| Memory retained per instance | 39.4x | 47.4x |
| Classes loaded | 2.1x | 2.1x |
| CPU of the whole process | 7.3x | 7.9x |

Java 21 and Java 8 x86 move the same way (Java 8 x86 warm build 37x to 43x, ready 161x to 173x; update
allocation 2.1x to 3.2x).

## What did not improve

- **Tiny updates still allocate more than JavaFX** (Separator 0.08x, Slider 0.21x, ScrollBar 0.22x,
  ProgressBar 0.46x). An update builds a new immutable element for each instance and reconciles it; JavaFX
  sets one property. The garbage removed from the reconcile narrowed the gap but cannot close it; only a
  path that updates the node from a changed binding without rebuilding the element would.
- **Painting text fields and tabs is still behind JavaFX in this series** (TextField 0.79x, Tabs 0.56x), and
  `TextArea` and `Tabs` came out worse than before (1.23x to 0.73x and 0.76x to 0.56x). In a loop that paints
  one screen many times after a warm-up, the text field frame went from 7.5 to 4.1 ms and a `Button` screen
  from 2.6 to 0.9 ms, so the change works; the benchmark paints the last of 8 passes of a fresh JVM, where the
  per-pixel loops are not fully compiled yet, and it does not show it. `Tabs` cannot benefit from the skipping
  (398 of 800 are in the window). The paint number is indicative, as before; this is not isolated further.
- **`Image` and `TableView` updates came out slower** (1.07x to 0.74x and 1.22x to 0.98x) although their
  allocation fell. The series has no repeated measurement of these two to say whether it is noise; the
  per-pass times are a few milliseconds.
- `Image` still allocates more when it becomes ready (0.71x): its native node is heavier than the
  `ImageView` of JavaFX.

## Reproduce

python -I scripts\generate-component-bench.py
scripts\measure-components.ps1 -Runs 5 -Passes 8 -Out docs\components-<date>   # about 2.5 hours
