# JXForge benchmark: JXML compiled vs interpreted, and FXML as reference

Two questions:

1. **What does compiling JXML to Java buy over interpreting the same file at runtime?** Same
   screens, same output: the tests check that every mode builds the identical `JXElement` tree
   and the same native layout. This is the comparison for the compiler itself.
2. **Where does that leave a screen against FXML on JavaFX?** Same 20 screens, but different
   work (see "Reading the FXML column"), so this is a reference, not a like-for-like ratio.

## Setup

| | |
|---|---|
| Screens | the 20 generated form screens of the FXML benchmark (`scripts/generate-fxml-bench.py`): toolbar of 8 buttons, 3 tabs of 15 labelled fields (TextField, ComboBox, CheckBox, DatePicker, Spinner), status bar. The JXML versions come from the same script; the 12 controls FXML injects are bound to controller getters, the buttons call a controller method |
| Modes | `javafx`: `FXMLLoader.load`, sequential, FX thread. `interpreted`: JXML read and checked on every load, built by reflection (as FXMLLoader reads its file every time). `template`: the same with the file read once. `compiled`: classes generated by `jxforge:generate`. `compiled-plain`: the same without constant hoisting |
| Stages | **load**: FXMLLoader.load vs building the element tree. **ready** (ready to paint): plus `Scene`, `applyCss` and `layout` at 1280x800, vs creating the native nodes, laying them out at 1280x800 and mounting the two other tabs ahead (`retainAhead`), as JavaFX builds every tab's content |
| JVMs | Oracle JDK 1.8.0_51 x86 (client VM, JavaFX 8 bundled, NanoVG natives); Oracle JDK 17.0.12 x64 and 21.0.8 x64 (OpenJFX 21.0.2) |
| Machine | Windows 11, Intel Core i5-12400F (12 threads), 16 GB, idle (overnight run) |
| Runs | 10 per mode, stage and JVM, each a fresh JVM, modes alternating within every run; 10 passes of 20 screens per run. Pass 1 is cold (class loading, interpreter), pass 10 warm. Medians, with the range of the 10 runs |
| Raw data | `jxforge-results-2026-10-21-<jvm>-<stage>.csv` and `-median.csv` (median, min, max per metric) |
| Reproduce | `scripts/measure-jxforge.ps1` (build steps in its header) |

Every run checks its result: 20 of 20 screens show the controller's status text, and the spinner
values and grid row indexes sum to the same totals as the FXML screens (4320 and 12600).

Findings:

1. **Building a screen is 30 to 40x faster compiled than interpreted** when warm (16.9 → 0.40 ms for 20
   screens on Java 17, 14.9 → 0.39 on Java 8 x86) and allocates 40x less. Most of that is
   reading the file: against a cached template the compiled code is still 2 to 4x faster and
   allocates 5x less, because it calls getters directly and shares constant subtrees.
2. **Cold, the first screen set builds in half the time on Java 17 and 21** (107 → 50 ms): no XML
   parser to load and warm up, no reflection. On the Java 8 32-bit client VM the gain is small
   (74 → 70 ms, ranges overlapping), and the compiled mode loads 75 classes more than the
   interpreted one. A likely cause, not verified: the client VM runs the 20 large generated
   classes in its bytecode interpreter the first time, while the XML parsing code it skips is
   cheap on that VM.
3. **Once the screen is made ready to paint, the gap narrows**: creating and laying out the
   native nodes costs more than building the tree, so compiled is 10 to 26% faster than a cached
   template warm (2.9 vs 3.3 ms on Java 17) and 12 to 24% faster cold. Against re-reading the
   file every time it stays about 8x faster warm.
4. **Constant hoisting helps building, not the rest.** It halves warm build time and cuts its
   allocation to a third (0.75 → 0.40 ms, 0.51 → 0.15 MB), because 2/3 of each screen has no
   binding. Cold it costs a little (constants are built when the class loads), and in the ready
   stage the difference is inside the noise, since the native nodes are created either way.
   Sharing the same element instances would pay off more when a screen is rebuilt in place,
   where the reconcile skips unchanged instances; that is not measured here.
5. **The compiled screens retain less memory**: 2.1 MB live after GC against 3.7 MB, since no
   template or reflection caches stay behind.

## 2. Against FXML on JavaFX (reference)

Time for 20 screens, milliseconds (median):

| JVM | Stage | FXML on JavaFX | JXML compiled | JXML interpreted |
|---|---|---:|---:|---:|
| Java 17 x64 | load, cold / warm | 802 / 354 | 50 / 0.40 | 107 / 16.9 |
| | ready, cold / warm | 2513 / 1036 | 176 / 2.93 | 219 / 22.8 |
| Java 21 x64 | load, cold / warm | 856 / 345 | 52 / 0.56 | 117 / 16.5 |
| | ready, cold / warm | 2509 / 1027 | 187 / 2.59 | 246 / 21.0 |
| Java 8 x86 | load, cold / warm | 821 / 542 | 70 / 0.39 | 74 / 14.9 |
| | ready, cold / warm | 2030 / 1120 | 179 / 2.39 | 201 / 19.2 |

Allocated per warm ready pass: FXML 582 MB on Java 17 (576 MB on Java 8 x86), JXML compiled
1.3 MB (1.2 MB). Live heap after GC (ready): 45 MB (16 MB) against 3.5 MB (3.9 MB). Peak working
set (ready): 1.6 GB on Java 17, where the default heap is sized from the 16 GB of RAM and the
collector lets it grow, 231 MB on Java 8 x86, against 111 MB and 36 MB.

### Reading the FXML column

The ratios are large because the two sides do different work, and most of the difference is the
architecture, not the compiler:

- `FXMLLoader` creates live JavaFX controls, each with its properties, listeners and, on
  `applyCss`, a skin and CSS matching against Modena. JXML builds immutable descriptions, and
  the native nodes have their look in the painter: there is no stylesheet pass to run here.
- Neither side paints in this test; painting and the first frame are measured in the UI
  comparisons (`ui-comparison-2026-09-25.md`, `fx-backends-comparison-2026-09-29.md`).
- The native text measurement keeps glyph widths cached across passes, which helps the warm passes.
- The element counts differ in form, not in content: the FXML fingerprint counts 2300 objects
  per pass (it counts each `Tab` and the toolbar's items list), the JXML one 2240 elements; the
  45 fields per screen, spinner values and grid positions are the same.

So the fair reading is: a native screen described in JXML gets to "ready to paint" an order of
magnitude or more sooner than the same screen in FXML, and the compiler's own share of that is
the interpreted → compiled column above.

## 3. Cost at build time

| | |
|---|---|
| Compiling the 20 files (fresh JVM, `JXForge` command line) | 140 ms (first run 227 ms); 240 ms including JVM start |
| JXML sources | 2,580 lines, 139 KB |
| Generated Java | 15,140 lines (757 per screen), 803 KB |
| Generated classes | 337 KB with hoisting, 324 KB without (the FXML files are 212 KB) |

The generated classes are about 2.4x the size of the JXML they replace in the jar: every element
is spelled out as calls. Unchanged files are skipped on the next build.

## Where JXML compiled is not ahead

- **Cold start on the Java 8 32-bit client VM**: 6% faster than interpreted, within the run spread.
- **Code size**: 337 KB of classes for 20 screens against 139 KB of JXML.
- **Classes loaded on Java 8 x86**: 982 against 907 for the interpreter.
- **Hoisting** does not help the ready stage and costs a little cold.
- CPU time per warm pass is below the 15.6 ms granularity of Windows process CPU, so it reads 0
  for the template and compiled modes; use the times instead.

## Threats to validity

- One machine, one run series; background load not recorded (the run was overnight on an idle
  machine).
- Synthetic screens: one shape, repeated 20 times. Screens with lists of rows need loops, which
  JXML does not have yet (they would go in a `<Slot>`).
- The ready stage does not paint, and the two sides do different styling work (see above).
